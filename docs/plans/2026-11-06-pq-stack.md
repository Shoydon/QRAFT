# Post-quantum application migration

The user requires the active application stack to use post-quantum cryptography.
This supersedes the classical Groth16/ECDSA browser integration plan.

Required application boundary:
- SHA3-512 note commitments/nullifiers, 64-byte secrets and a depth-32 tree.
- Transparent V5 hash/FRI withdrawal proof; no pairing wrapper or trusted setup.
- ML-DSA-44 user authorization; no ECDSA/P-256 user-custody fallback.
- Native ETH deposits and withdrawals, with independently pinned deployment identity.
- Anonymous RPC reads remain required.

The previous classical flow must not remain the default or silently take over.
The imported native V5/PQ-account developer flow now has browser public-proof
export, independent public encoding, local account provisioning and native UI integration.
The existing live pool denomination is 0.0001 ETH. The source test paymaster is
closed to one account, so it cannot be presented as generic user infrastructure.

External boundary: Ethereum/devnet consensus, network TLS and Nym's internal
cryptography are not established as end-to-end post-quantum. Operator gas-service
ECDSA is confined to the external gas/provisioning carrier and excluded from
the user-custody claim. This application boundary, with documented external
limits, is the approved scope.
No fully post-quantum entire-stack claim is allowed solely from an ML-DSA signer.

Implementation: pinned native sources and browser artifacts; SHA3-512 notes;
ML-DSA signer and immutable-account recovery; public-only proof encoding; exact
intent and receipt checks; public computation and recovery journals; explicit
wallet/note backup gates. Keep the browser witness and user signing seed local.
Validation covers fresh provisioning/deposit, backup restore, browser proving,
public encoder mutation/integrity checks, staged EVM verification, native payout
and spent-note rejection. Current evidence and limits belong in the security
document and integration report, rather than in a blanket entire-stack claim.
